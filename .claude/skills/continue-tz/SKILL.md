# Продолжение работы по ТЗ

## 1. Определить активное ТЗ

| ТЗ                              | Статус                  | Файл статуса           |
| ------------------------------- | ----------------------- | ---------------------- |
| `docs/saas/TZ-SaaS.md` (SaaS)   | **активное**            | `docs/saas/STATUS.md`  |
| `docs/TZ.md` (базовое, этапы 1–14) | выполнено, справочное | `docs/STATUS.md`       |

Если пользователь явно назвал другое ТЗ — работать по нему. Иначе — по активному. Базовое ТЗ остаётся источником
требований безопасности и контракта инструментов (в SaaS-ТЗ ссылки вида «Б§8.2»).

## 2. Понять, где остановились

1. Прочитать файл статуса активного ТЗ: «Текущий этап», «Следующий шаг», «План этапа», «Открытый PR».
2. Проверить открытые PR репозитория `aiprocadm/mcp_bitrix` (в облачной сессии — инструментами GitHub MCP `mcp__github__list_pull_requests`, `gh` недоступен).
   - Есть открытый PR прошлого среза и он не влит → продолжать в его ветке (доделать замечания/CI), новый срез поверх невлитого не начинать.
   - PR влит → новая работа начинается от свежего `origin/main`.
3. Прочитать раздел ТЗ текущего этапа **целиком** (не по памяти) и связанные разделы, на которые он ссылается.
4. Сверить статус с кодом (`git log --oneline -20`, файлы из колонки «Где»): статус мог отстать от кода.

## 3. Ветка

- Если среда задала рабочую ветку (облачная сессия: «Develop on branch …») — работать в ней. Если её PR уже влит — пересоздать ветку от `origin/main` (`git fetch origin main && git checkout -B <ветка> origin/main`).
- Локально без заданной ветки — worktree `.claude/worktrees/<имя>` и ветка от `origin/main` (как в `CLAUDE.md`).

## 4. Сделать срез

- Срез — законченный, проверяемый кусок этапа (обычно 1 пункт «Плана этапа»), а не весь этап за раз, если этап большой.
- Решения ТЗ (§3 SaaS-ТЗ) не пересматривать. Неясность → принять разумное допущение, записать его в «Решения, принятые по ходу» файла статуса и продолжать. Владельцу вопросов не задавать без крайней необходимости.
- Непреложные правила `CLAUDE.md` действуют всегда (без заглушек `success:true`, без автоподтверждения, секреты вне Git/логов/ответов, `fetch` только в `src/bitrix/client.ts`, новый внешний API — только по официальной документации со ссылкой).
- Режим `single` не ломать: весь существующий набор тестов зелёный на каждом срезе.
- Документация Bitrix24: сайт apidocs может быть недоступен из среды; официальный исходник — `git clone --depth 1 https://github.com/bitrix24/b24restdocs` во временную папку (структура путей совпадает с apidocs.bitrix24.ru).

## 5. Проверки перед PR (все обязательны)

```bash
npm run lint && npx prettier --check . && npm run typecheck && npm test && npm run build \
  && npm run check:secrets && npm run mcp:smoke -- --transport stdio --config tests/fixtures/mock.env
```

Зависимости в облачной сессии ставит SessionStart-хук (`.claude/hooks/session-start.sh`); если `node_modules` нет — `npm ci`.

## 6. Обновить статус и документацию

- Файл статуса активного ТЗ: дата, «Текущий этап», «Следующий шаг» (конкретный следующий срез — чтобы следующая сессия начала без раздумий), отметка в таблице этапов, раздел «Сделано» (что, где, чем проверено, что НЕ проверено: mock ≠ реальный портал ≠ реальный платёж), новые грабли.
- Если этап завершён — перевести «Текущий этап» на следующий и расписать его «План этапа» по пунктам.
- Изменились инструменты → `npm run schemas:export` (каталог `docs/tools-catalog.md`).

## 7. Коммит, push, PR

- Коммит с понятным русским сообщением; push в рабочую ветку; PR (черновик), если открытого для ветки нет.
- Описание PR: этап и срез ТЗ, что сделано, что проверено, что не проверено (честно: `not-run`/`blocked`).
- После создания PR — следить за CI/ревью и доводить до зелёного.

## 8. Итог пользователю

Коротко: какой срез сделан, ссылка на PR, что проверено и что нет, какой следующий шаг записан в статус.
