# Техническое задание: MCP-сервер для Bitrix24 как сервис по подписке (SaaS)

Версия 1.0 от 2026-09-25. Статус работ — `docs/saas/STATUS.md`. Правила работы — `CLAUDE.md`.

Базовое ТЗ `docs/TZ.md` (этапы 1–14) **выполнено** и остаётся в силе: все требования безопасности (§8), контракт
инструментов (§9, §15), клиент Bitrix24 (§14) и тесты (§19) действуют и в SaaS-режиме. Этот документ описывает только
то, что добавляется или меняется, чтобы один экземпляр сервиса обслуживал много клиентов по платной подписке.
Номера разделов базового ТЗ пишутся как «Б§8.2».

## 0. Как пользоваться документом

- Работа идёт этапами §19 (S0–S10), каждый этап — один или несколько срезов с PR. Текущий этап и сделанное — в `docs/saas/STATUS.md`.
- Решения §3 приняты и не пересматриваются без владельца. Где ТЗ говорит «допущение», исполнитель действует по нему и не ждёт ответа (вопросы — §20, они не блокируют работу).
- Однопользовательский режим (текущий, `DEPLOYMENT_MODE=single`) обязан продолжать работать без изменений в поведении: все существующие тесты остаются зелёными на каждом срезе.
- Любой новый внешний API (Bitrix24, ЮKassa, спецификация MCP) — только по официальной документации, ссылка фиксируется в коде или в ADR (как Б§15.4).

## 1. Цель и результат

Сервис, в котором любой клиент с облачным Bitrix24 без технических знаний:

1. Устанавливает приложение «MCP для Bitrix24» из Маркета (или по ссылке) на свой портал.
2. Входит в личный кабинет через свой аккаунт Bitrix24, выбирает тариф, оплачивает.
3. Получает адрес MCP-сервера и за 2 минуты подключает его в Claude (Desktop/Code/claude.ai) или ChatGPT.
4. Каждый сотрудник портала работает через MCP **со своими правами Bitrix24**, подтверждает записи в кабинете.
5. Владелец сервиса видит клиентов, подписки, платежи и нагрузку, не видя содержимого порталов.

Результат проекта — работающий публичный сервис: код, инфраструктура, биллинг, кабинет, юридические шаблоны, пилот на
реальных порталах (§18).

### 1.1. Не входит в первую версию

- Коробочный Bitrix24 (on-premise) в SaaS: такие клиенты используют self-hosted режим `single` (он остаётся).
- Собственная LLM/чат внутри сервиса: сервис — только MCP-сервер, модель — у клиента (Claude, ChatGPT и др.).
- Партнёрская программа, white-label, мультивалютность, иностранные платёжные системы.
- Мобильное приложение. Кабинет — адаптивная веб-страница.

пользователя (§5.2). Это первая работа (этап S1).

## 3. Принятые решения

| №   | Решение                                                                                                                                                       | Почему                                                                                                                    |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| D1  | Арендатор (tenant) = один портал Bitrix24, ключ — `member_id` портала. Подписка оформляется на портал, места считаются по активным пользователям              | Совпадает с моделью Маркета Bitrix24 и с тем, как клиенты покупают (на компанию)                                          |
| D2  | Подключение портала — **тиражное приложение** Bitrix24 (OAuth, Маркет). Вебхуки в SaaS не принимаются                                                         | Вебхук = права одного сотрудника и секрет в URL; OAuth даёт токены каждого пользователя, отзыв при удалении приложения    |
| D3  | Каждый сотрудник работает **своим** OAuth-токеном Bitrix24; сервисных «суперпользователей» нет                                                                | Права Bitrix24 соблюдаются самим порталом; сервис не может прочитать больше, чем видит сотрудник                          |
| D4  | Вход в сервис — **через Bitrix24** (OAuth тиражного приложения), без отдельного пароля. Email нужен только для счетов и уведомлений                           | Нет своей базы паролей; личность и портал подтверждаются одним действием                                                  |
| D5  | Сервис сам является **сервером авторизации MCP** (OAuth 2.1 + PKCE, метаданные RFC 8414/9728, динамическая регистрация клиентов), вход делегируется Bitrix24  | Claude и ChatGPT подключают удалённые MCP именно так; внешний IdP добавил бы ещё одну учётную запись пользователю         |
| D6  | Хранилище SaaS — **PostgreSQL**, у каждой таблицы арендатора `tenant_id NOT NULL` + Row Level Security; кэш/лимиты/блокировки — **Redis**                     | Несколько экземпляров сервиса, изоляция на уровне БД, а не только кода                                                    |
| D7  | Шифрование конвертом: у арендатора свой ключ данных (DEK), он зашифрован главным ключом (KEK) из файла/KMS; токены Bitrix24 и планы — под DEK арендатора      | Утечка строк одной таблицы не раскрывает чужие токены; удаление DEK = криптоудаление данных арендатора                    |
| D8  | Платежи — **ЮKassa** (карта, СБП; рекуррентные списания по сохранённому способу оплаты; чеки 54-ФЗ через ЮKassa). Юрлицам — оплата по счёту с ручной отметкой | Российский рынок; Маркет Bitrix24 допускает оплату сервису напрямую (модель «бесплатное приложение с платными функциями») |
| D9  | Платёжный провайдер скрыт за интерфейсом `PaymentProvider`; второй провайдер добавляется без изменения биллинга                                               | Риск блокировок/смены тарифов провайдера                                                                                  |
| D10 | Тарифы и квоты — **данные**, а не код (таблица `plans`, правка из панели владельца); цены §9 — допущение по умолчанию                                         | Владелец меняет цены без релиза                                                                                           |
| D11 | Учёт использования = число вызовов инструментов, дошедших до Bitrix24, и число выполненных записей; жёсткие лимиты без автоматических доплат                  | Предсказуемый счёт для клиента; нет «сюрпризов» в РФ-практике                                                             |
| D12 | Подтверждение записи — в кабинете по ссылке `approvalUrl` из `APPROVAL_REQUIRED`; CLI-подтверждение остаётся только для `single`                              | У пользователя SaaS нет доступа к серверу; ссылка открывается в браузере рядом с чатом                                    |
| D13 | Хостинг и все БД — в РФ; данные портала сервис за рубеж не передаёт (модель вызывает клиентский MCP-клиент)                                                   | 152-ФЗ ч.5 ст.18 (локализация) для учётных данных пользователей сервиса                                                   |
| D14 | Один кодовый базис: `DEPLOYMENT_MODE=single\|saas`. `single` — поведение как сейчас                                                                           | Не поддерживать два продукта; self-hosted остаётся для коробки и параноидальных клиентов                                  |
| D15 | Владелец сервиса не имеет инструмента «посмотреть данные клиента»: поддержка видит только метаданные, журнал и ошибки без тел                                 | Доверие клиентов и минимизация ПДн; имперсонация запрещена                                                                |

## 4. Роли и сценарии

| Роль                               | Кто это                                                                      | Что может                                                                                                                                 |
| ---------------------------------- | ---------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| Владелец сервиса (`service_owner`) | Вы                                                                           | Тарифы, клиенты, платежи, блокировки, объявления, метрики. Не видит содержимого порталов (D15)                                            |
| Поддержка (`support`)              | Сотрудники владельца                                                         | Метаданные арендатора, статусы, журнал ошибок без тел запросов; продление пробного периода; всё — в журнале действий поддержки            |
| Администратор арендатора           | Администратор портала Bitrix24, установивший приложение (или назначенный им) | Подписка и оплата, модули, роли пользователей, лимиты по пользователям, политика подтверждений, отключение пользователей, удаление данных |
| Пользователь арендатора            | Сотрудник портала, вошедший через Bitrix24                                   | Подключить MCP-клиент, работать инструментами в пределах своих прав Bitrix24 и роли в сервисе, подтверждать свои записи                   |

Роль пользователя в сервисе (`reader`/`operator`/`administrator` из Б§10.4) назначает администратор арендатора; по
умолчанию новый пользователь — `operator` без удалений. Роль сервиса только **сужает** права Bitrix24, никогда не расширяет.

Ключевые сценарии (каждый — приёмочный тест §18):

1. **Онбординг**: установка приложения → кабинет → пробный период → MCP URL и инструкция → первый вызов из Claude.
2. **Второй сотрудник**: открывает кабинет по ссылке, входит через Bitrix24, подключает свой MCP-клиент; видит только то, что разрешено ему в Bitrix24.
3. **Запись**: модель вызывает `task_create` → `APPROVAL_REQUIRED` + `approvalUrl` → пользователь открывает ссылку, видит план, подтверждает → модель повторяет вызов → задача создана один раз.
4. **Оплата**: окончание пробного периода → оплата картой → автосписание через месяц → чек на email.
5. **Неоплата**: списание не прошло → 7 дней льготного периода с баннером → блокировка инструментов (данные сохраняются 30 дней) → оплата → разблокировка.
6. **Удаление приложения с портала**: `OnAppUninstall` → токены удалены, подписка остановлена, данные удаляются по регламенту §14.
7. **Отзыв доступа**: администратор отключает сотрудника → его MCP-токены и незавершённые подтверждения аннулируются сразу.

## 5. Архитектура

### 5.1. Компоненты

```
MCP-клиент (Claude/ChatGPT) ──HTTPS──► nginx ──► mcp-app (N экземпляров, Node 24)
                                                   │  /mcp            — MCP Streamable HTTP (как сейчас)
                                                   │  /oauth/*        — сервер авторизации MCP (§7)
                                                   │  /.well-known/*  — метаданные RFC 8414 / RFC 9728
                                                   │  /b24/*          — установка/события приложения Bitrix24 (§8)
                                                   │  /app/*          — кабинет клиента (§11)
                                                   │  /owner/*        — панель владельца (§11.3)
                                                   │  /billing/hooks  — уведомления ЮKassa (§10)
                                                   ├─► PostgreSQL (данные, RLS)   ├─► Redis (лимиты, блокировки, сессии)
                                                   └─► Bitrix24 порталов клиентов (OAuth пользователя)
worker (тот же код, режим worker): продления подписок, обновление токенов, очистка, отчёты, письма
```

Один образ, режимы процесса: `web` и `worker`. Горизонтальное масштабирование `web` без липких сессий: состояние MCP-сессий,
курсоров, лимитов — в Redis/PostgreSQL.

### 5.2. Путь запроса в SaaS

1. MCP-запрос с `Authorization: Bearer <access token сервиса>`.
2. Проверка JWT (подпись, `iss`, `aud` = ресурс MCP, срок, отзыв по `jti`/поколению) — как `mcp-auth.ts`.
3. По `sub` → пользователь → арендатор. Проверки: пользователь активен, арендатор не заблокирован, подписка позволяет (§9.3), модуль инструмента входит в тариф и включён администратором.
4. Сборка **контекста арендатора** (`TenantScope`): провайдер `BitrixOAuthUserProvider(tenant, user)`, клиент Bitrix24 портала (лимитер портала общий для всех экземпляров), политики арендатора, output policy, хранилища, отфильтрованные по `tenant_id`.
5. Обычный путь Б§4.3: схема → политика → handler (`ctx.bitrix` уже клиент нужного портала и пользователя) → аудит → учёт использования (§9.2) → ответ.

`ToolContext` получает поле `tenant: { id, plan, limits }`; инструменты его не используют для доступа к данным — только ядро.
Кэш `TenantScope` — LRU на экземпляр с TTL 60 с и немедленной инвалидацией по событию (отзыв, смена тарифа) через Redis pub/sub.

### 5.3. Режим single

`DEPLOYMENT_MODE=single`: неявный арендатор `local`, вебхук, SQLite, CLI-подтверждение, `/admin` — ровно как сейчас.
Всё новое (кабинет, биллинг, AS, `/b24/*`) в этом режиме не регистрируется. Проверка конфигурации запрещает смешение
(например, `DEPLOYMENT_MODE=saas` с `BITRIX_AUTH_MODE=webhook` → `CONFIG_INVALID`).

## 6. Данные

### 6.1. Хранилище

- PostgreSQL ≥ 16 в РФ. Доступ через слой репозиториев с асинхронным интерфейсом; текущие синхронные хранилища SQLite оборачиваются тем же интерфейсом для `single`.
- Каждая таблица арендатора: `tenant_id NOT NULL`, внешний ключ, индекс, политика RLS `USING (tenant_id = current_setting('app.tenant_id')::uuid)`. Подключение приложения — роль без `BYPASSRLS`; `SET LOCAL app.tenant_id` в каждой транзакции арендатора. Служебные задачи worker по нескольким арендаторам — отдельная роль, только перечисленные таблицы.
- Миграции версионные, вперёд-совместимые (expand → migrate → contract), запуск отдельной командой до выката.

### 6.2. Основные таблицы

### 6.3. Сроки хранения (допущения, правятся владельцем)

Аудит — 90 дней (Б§8.6). Технические логи — 14 дней. Данные арендатора после окончания подписки — 30 дней, затем
криптоудаление (удаление DEK) и физическое удаление строк. Платёжные документы — по требованиям бухучёта (5 лет),
отдельно от данных портала.

## 7. Аутентификация и авторизация

### 7.1. Сервер авторизации MCP (D5)

По актуальной спецификации авторизации MCP (сверить версию при реализации, ссылка в ADR):

- `/.well-known/oauth-protected-resource` (RFC 9728) — уже есть, указывает на собственный AS.
- `/.well-known/oauth-authorization-server` (RFC 8414): `authorization_endpoint`, `token_endpoint`, `registration_endpoint`, `revocation_endpoint`, `code_challenge_methods_supported: ["S256"]`.
- Динамическая регистрация клиентов (RFC 7591) для публичных клиентов; при поддержке спецификацией — Client ID Metadata Documents. Лимит регистраций с одного IP; неиспользуемые клиенты удаляются через 30 дней.
- Authorization Code + PKCE (S256 обязателен), параметр `resource` (RFC 8707) обязателен и должен совпадать с URL MCP; `redirect_uri` — точное совпадение с зарегистрированным.
- Access token — JWT 10 минут, `aud` = ресурс MCP, `sub` = внутренний ID пользователя, `tid` = арендатор, `scope` (`mcp:read`, `mcp:write`). Refresh token — непрозрачный, ротация при каждом использовании, 30 дней, обнаружение повторного использования → отзыв всей цепочки.
- Ключи подписи — ротация, публикация JWKS; старый ключ живёт до истечения выданных токенов.

### 7.2. Вход через Bitrix24 (D4)

Шаг `authorize` сервиса отправляет пользователя на OAuth Bitrix24 (адрес портала вводит пользователь или берётся из
установки). После возврата: обмен `code` (живёт 30 с) на токены Bitrix24, `profile`/`user.current` → пользователь; портал
по `member_id` должен быть установлен (иначе — страница «установите приложение»). Затем экран согласия сервиса: какой
клиент (имя из DCR), какие права (`mcp:read`/`mcp:write`), какой портал. Согласие запоминается на пару пользователь-клиент.

### 7.3. Токены Bitrix24 пользователя

- `access_token` живёт 1 час, `refresh_token` — 180 дней (документация Bitrix24 OAuth). Обновление — single-flight на пару (портал, пользователь) через блокировку Redis и поле поколения в БД (Б-тест T17 распространяется на кластер).
- Отказ обновления (приложение удалено, истёк платный период приложения, пользователь уволен) → пользователь помечается «нужен повторный вход», MCP возвращает `BITRIX_AUTH_FAILED` с `nextAction` и ссылкой на кабинет.
- Токены никогда не попадают в ответы, логи, кабинет, панель владельца.

### 7.4. Отзыв

Отключение пользователя, удаление приложения, блокировка арендатора → немедленно: отзыв refresh-токенов сервиса,
инкремент поколения пользователя (access-токены с меньшим поколением отклоняются), удаление токенов Bitrix24 (при
удалении приложения), аннулирование подготовленных и подтверждённых, но не исполненных операций (Б-тест T48).

## 8. Подключение портала (тиражное приложение)

- Приложение регистрируется в кабинете разработчика Bitrix24 как тиражное (для Маркета) и параллельно как локальное — для пилотов до публикации. Права (scope) — перечень модулей из матрицы Б§10.4; при установке запрашиваются все, модули включаются тарифом и администратором.
- Установка: обработчик установки `/b24/install` (документированный installation callback / мастер установки) сохраняет портал и токены установившего, создаёт арендатора со статусом `trialing`, регистрирует обработчик `OnAppUninstall` и отдаёт страницу «Готово — откройте кабинет».
- `OnAppUninstall` → §4 сценарий 6. Подлинность события проверяется по `application_token` установки (документация событий), чужие вызовы отклоняются.
- Встроенная страница приложения в интерфейсе Bitrix24 (placement по умолчанию) показывает кабинет арендатора (iframe с проверкой подписи запуска) — основной вход для пользователей портала.
- `app.info` периодически (worker, раз в сутки) — статус приложения и лицензии портала; истёкшая лицензия Bitrix24/REST — предупреждение в кабинете, а не молчаливые ошибки.
- Требования к публикации в Маркете (раздел документации market/*) — чек-лист в этапе S9; до публикации сервис работает для пилотных порталов через локальное приложение.

## 9. Тарифы, квоты и учёт

### 9.1. Тарифы по умолчанию (допущение D10; цены и лимиты правит владелец)

| Тариф   | Цена в месяц | Порталов | Пользователей | Вызовов в месяц | Записей в месяц | Модули                                      | Удаления (этап 14) |
| ------- | ------------ | -------- | ------------- | --------------- | --------------- | ------------------------------------------- | ------------------ |
| Пробный | 0 ₽, 14 дней | 1        | 3             | 1 000           | 100             | Все                                         | Нет                |
| Старт   | 990 ₽        | 1        | 3             | 5 000           | 300             | CRM, задачи, календарь, чаты, диск, система | Нет                |
| Команда | 2 990 ₽      | 1        | 15            | 30 000          | 3 000           | Все                                         | Нет                |
| Бизнес  | 7 990 ₽      | 1        | 50            | 150 000         | 15 000          | Все                                         | Да                 |

Годовая оплата — 10 месяцев вместо 12. Места сверх тарифа не продаются поштучно в v1: следующий тариф. Пробный период — один
на портал (`member_id`), повторная установка его не обнуляет.

### 9.2. Учёт использования (D11)

- «Вызов» — `tools/call`, прошедший проверки политики и дошедший хотя бы до одного запроса к Bitrix24 (ошибки валидации и отказы политики не считаются). «Запись» — операция MutationExecutor в статусе `succeeded` или `unknown`.
- Счётчик увеличивается атомарно в Redis, сбрасывается в PostgreSQL агрегатами раз в минуту и при остановке процесса; расхождение при падении — не больше минуты работы (честно указывается в кабинете как «данные с задержкой до 1 минуты»).
- Кабинет: использование за период, по пользователям и инструментам; владелец — по арендаторам.

### 9.3. Исчерпание и ограничения

- 80% квоты — уведомление администратору (кабинет, email). 100% — новые вызовы получают `QUOTA_EXCEEDED` (новый код ошибки, класс «нет автоповтора», `nextAction`: сменить тариф/дождаться периода). Диагностика (`bitrix_connection_info`, `bitrix_server_version`, `operation_status`) доступна всегда.
- Администратор может задать лимит на пользователя (например, 500 вызовов в сутки) — защита от зацикленного агента.
- Модуль вне тарифа → инструмент скрыт в `tools/list`, прямой вызов → `FEATURE_UNAVAILABLE` с причиной «не входит в тариф».
- Лимит входящих запросов Б§8.6 действует на пользователя; дополнительно — на арендатора (сумма) и глобальный (защита сервиса).

## 10. Биллинг

### 10.1. Платежи (D8, D9)

- Интерфейс `PaymentProvider`: `createPayment`, `chargeSaved`, `getPayment`, `refund`, `verifyNotification`. Первая реализация — ЮKassa (сверить API и требования при реализации по официальной документации ЮKassa, ссылку зафиксировать в ADR).
- Первая оплата — через страницу провайдера с сохранением способа оплаты (согласие на автосписание — явная галочка). Продления — рекуррентное списание сохранённым способом из worker.
- Уведомления провайдера: принимаются только от адресов провайдера и **всегда** перепроверяются запросом статуса платежа к API провайдера; обработка идемпотентна по ID платежа. Неизвестный платёж — журнал и игнор.
- Чеки 54-ФЗ — через провайдера (данные чека: услуга «Доступ к сервису MCP для Bitrix24, тариф X, период»). Реквизиты продавца и ставка НДС — конфигурация.
- Юрлица: счёт PDF из кабинета, оплата вручную, отметка оплаты владельцем в панели (с журналом). Автоматическая сверка банковской выписки — вне v1.
- Деньги только в копейках (целые), без float (как Б§9.6).

### 10.2. Жизненный цикл подписки

```
trialing ──оплата──► active ──продление ok──► active
   │                  │ продление не прошло
   │ истёк            ▼
   └──────────► past_due (7 дней: всё работает, баннер, 3 попытки списания) ──оплата──► active
                      │ не оплачено
                      ▼
                 suspended (инструменты → SUBSCRIPTION_INACTIVE, кроме диагностики; кабинет и оплата доступны; данные хранятся 30 дней)
                      │ 30 дней                         ▲ оплата
                      ▼                                 │
                 deleted (криптоудаление)  ◄── uninstalled (OnAppUninstall; данные 30 дней для восстановления при переустановке)
cancel → действует до конца оплаченного периода → suspended
```

Смена тарифа: повышение — сразу, с доплатой пропорционально остатку периода; понижение — с начала следующего периода,
если текущее использование в пределах нового тарифа (иначе — предупреждение, что лишние пользователи/модули будут
отключены). Возвраты — только вручную владельцем через панель (провайдер `refund`), с записью в журнал.

## 11. Кабинет и панели

### 11.1. Кабинет клиента (`/app`)

Серверный рендер, без обязательного JavaScript (как текущая `/admin`), адаптивная вёрстка, CSP `default-src 'self'`.
Сессия — cookie `HttpOnly; Secure; SameSite=Lax` (вход через OAuth Bitrix24 требует возврата с другого домена), CSRF-токены.

Страницы:

1. **Начало**: статус подписки, использование, кнопка «Подключить к Claude/ChatGPT».
2. **Подключение**: адрес MCP, пошаговые инструкции с картинками для Claude Desktop, Claude Code, claude.ai, ChatGPT; кнопка «Проверить подключение» (последний успешный вызов пользователя).
3. **Подтверждения**: ожидающие планы пользователя, план целиком (как `approval:review`), кнопки «Подтверждаю»/«Отклоняю»; для удалений и массовых замен — повторный ввод слова `ПОДТВЕРЖДАЮ` и свежий вход (не старше 15 минут).
4. **История**: операции пользователя (статус, объект, время), без тел ответов Bitrix24.
5. **Администрирование арендатора** (роль администратора): пользователи и роли, модули, политика подтверждений (кто подтверждает: сам пользователь / администратор для удалений), лимиты на пользователя, output policy (профили полей), подписка и оплата, счета, удаление всех данных.
6. **Загрузка файлов** для `disk_upload_file` (как web-upload `/admin`, сканер обязателен).

### 11.2. Подтверждение из чата (D12)

`APPROVAL_REQUIRED` в SaaS дополнительно содержит `approvalUrl` (`/app/approvals/<operationId>`), срок и короткий
код для сверки. Модель показывает ссылку пользователю; после подтверждения пользователь пишет «готово», модель повторяет
вызов с `approvalId`. Подтвердить может только сам пользователь (или администратор арендатора, если так настроено для
операций повышенного риска). Ссылка без входа ничего не раскрывает.

### 11.3. Панель владельца (`/owner`)

Арендаторы (домен, тариф, статус, использование, последние ошибки по кодам), платежи, ручные операции (продлить пробный
период, отметить оплату счёта, возврат, блокировка с причиной), тарифы, объявления в кабинете, метрики сервиса. Вход —
отдельная учётная запись владельца с паролем и TOTP (не через Bitrix24). Каждое действие — в `support_actions`.

## 12. Изоляция и безопасность

Все требования Б§8 действуют. Дополнительно:

1. **Изоляция арендаторов** проверяется тремя слоями: RLS в БД, `tenant_id` в каждом ключе кэша/курсора/операции/лимита, и тесты «чужой арендатор» на каждый класс данных (§17).
2. Курсор, `operationId`, `approvalId`, `fileToken` другого арендатора или пользователя → тот же ответ, что и для несуществующего (не раскрывать существование).
3. Секреты: KEK — вне БД и бэкапов (файл с правами 0600 или KMS); DEK арендатора — в БД под KEK; токены Bitrix24 и планы операций — под DEK.
4. SSRF: исходящие запросы только на домены порталов, установивших приложение (`*.bitrix24.*` облака), OAuth-серверы Bitrix24 и API платёжного провайдера; адрес портала при входе проверяется по списку установок, произвольный адрес не запрашивается.
5. Защита кабинета: CSRF, CSP, rate limit входа и подтверждений, `X-Frame-Options`/`frame-ancestors` — только для страницы приложения внутри Bitrix24.
6. Сервис не хранит тексты ответов Bitrix24 дольше, чем нужно для курсора (TTL Б§14.3) и результата операции (минимальный).
7. Злоупотребления: лимиты регистрации DCR, лимиты пробных периодов на `member_id`, блокировка арендатора владельцем с уведомлением.
8. Уязвимости зависимостей — `npm audit` в CI, обновления раз в месяц; секреты в CI отсутствуют.

## 13. Эксплуатация

- Контейнеры: `web` ×2+ за nginx (HTTPS, HSTS), `worker` ×1 (с блокировкой лидера в Redis), PostgreSQL (управляемый или с репликой), Redis (с персистентностью для счётчиков). Хостинг в РФ (D13). Профили: `docker compose` для небольших инсталляций, манифесты Kubernetes — опционально.
- Мониторинг: метрики (запросы, ошибки по кодам, задержки p95 собственной обработки, очередь лимитера на портал, списания), логи в формате JSON без ПДн, алерты (ошибки 5xx, недоступность Bitrix OAuth, неуспешные продления, заполнение диска).
- Бэкапы PostgreSQL — ежедневно, шифрованные, хранение 14 дней, ежемесячная проверка восстановления (Б-тест T45 для кластера). KEK хранится отдельно от бэкапа.
- Выкат без простоя: миграции expand/contract, `web` по одному; откат — предыдущий образ + совместимая схема.
- Цель доступности — 99,5% в месяц (согласуемая цель, не гарантия в оферте без решения владельца).
- Нагрузка v1: 200 арендаторов, 2 000 пользователей, 50 вызовов/с в пике на весь сервис; узкое место — лимиты Bitrix24 на портал, а не сервис.

## 14. Персональные данные и юридическое

Не юридическое заключение; документы проверяет юрист владельца до запуска продаж.

- Для **данных порталов** клиент — оператор, сервис — лицо, обрабатывающее по поручению (ч.3 ст.6 152-ФЗ): поручение включается в оферту; сервис обрабатывает только для исполнения вызовов пользователя, не использует для других целей, удаляет по регламенту §6.3.
- Для **учётных данных пользователей сервиса** (ФИО, email, платежи) сервис — оператор: политика обработки ПДн на сайте, согласия в кабинете, уведомление Роскомнадзора, базы в РФ (D13).
- Передача данных модели: вызовы делает MCP-клиент пользователя (Claude/ChatGPT) — выбор клиента и основания трансграничной передачи — ответственность клиента-оператора; это явно сказано в оферте и в кабинете (Б§8.4).
- Документы-шаблоны (этап S9): оферта с приложением «Поручение на обработку ПДн», политика обработки ПДн, согласие на обработку, условия автосписания, SLA-приложение (если владелец решит).
- Удаление по запросу: администратор арендатора → «Удалить все данные» (§11.1 п.5) → немедленное аннулирование токенов и криптоудаление; подтверждение на email.

| S13 | Удаление всех данных арендатора                                                                 | Integration      | Токены отозваны, DEK удалён, строки удалены; платёжные документы сохранены отдельно         |
| S14 | Режим `single` после всех изменений                                                             | Regression       | Все тесты базового ТЗ зелёные, поведение без изменений                                      |
| S15 | Лимитер портала при трёх экземплярах                                                            | Integration      | Суммарная частота к одному порталу не превышает настроенной                                 |
| S16 | Учёт использования при падении процесса                                                         | Integration      | Потеря не больше минуты счётчиков; двойного счёта нет                                       |
| S17 | Ошибка обновления токена Bitrix24 (приложение удалено/лицензия истекла)                         | Integration      | `BITRIX_AUTH_FAILED` с понятным `nextAction` и ссылкой; нет бесконечных повторов            |

Проверка честная (как Б§20): mock ≠ реальный портал ≠ реальный платёж. Тестовый магазин ЮKassa и тестовый портал
Bitrix24 — для приёмки S10.
