# Выгрузки, подсчёты, звонки и диалоги на сервере (заявка 2026-10-13)

Цель — меньше токенов: сервер сам листает страницы портала, считает и складывает большие списки в файл, а в разговор
возвращает короткий итог (путь к файлу, число строк, 5 строк для проверки, таблицу итогов).

## CRM

| Инструмент    | Что делает                                                                                                                     |
| ------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| `crm_export`  | Вся выборка сделок/лидов/контактов/компаний по фильтру → XLSX или CSV в `DOWNLOAD_DIR`; колонки с именами и ссылка на карточку |
| `crm_count`   | Количество по фильтру; с `groupBy` — таблица итогов по полю или по дате (`period`), сумма `sumField`                           |
| `crm_orphans` | Компании/контакты без сделок, лидов или дел за `activityDays` дней → файл и число                                              |

- Обход — по возрастанию ID пачками по 50 с `>ID` и `start=-1` (способ выгрузки больших объёмов из документации Bitrix24):
  без подсчёта `total` на каждой странице и без сдвига от новых записей. Продолжение — серверный `cursor`
  (одноразовый, зашифрован, привязан к фильтру); черновик файла `<имя>.part.jsonl` при повторе с тем же курсором
  обрезается до сохранённой длины — строки не задваиваются.
- Скорость ограничена `BITRIX_REQUESTS_PER_SECOND` (по умолчанию 1 запрос/с ≈ 3000 записей в минуту). За вызов —
  `maxSeconds` (по умолчанию 90), дальше `complete=false` и `cursor`.
- Имена: сотрудники — `user.get` без фильтра `ACTIVE` (находит и уволенных), компании/контакты — `crm.*.list` с `@ID`,
  стадии/источники/типы — `crm.status.list`, воронки — `crm.category.list`. Ошибка справочника не прерывает выгрузку
  (пустое имя + предупреждение).
- Связи в `crm_orphans`: сделки/лиды пачкой `@COMPANY_ID`/`@CONTACT_ID`; у контакта в ответе виден только основной
  контакт сделки, поэтому кандидаты «без сделок» проверяются по одному (`CONTACT_ID`). Дела — где запись владелец
  (`OWNER_TYPE_ID` + `@OWNER_ID`), созданные за `activityDays` дней.
- `!%ПОЛЕ` («не содержит»): на живом портале `!%TITLE` у компаний вернул совпадения вместо исключения. Условие больше
  не уходит в портал — сервер добавляет поле в выборку и исключает совпадения сам (без учёта регистра) во всех списках
  CRM, выгрузках и подсчётах.
- `crm_list_records`: `compact=true` (ID, название, дата, ответственный, без пустых полей), `withNames=true`
  (`ASSIGNED_BY_NAME`, `COMPANY_NAME`, `STAGE_NAME`, `SOURCE_NAME`…). Курсор больше не привязан к `pageSize`
  (во всех списках на `legacyListPage`/`offsetPage`).
- `employees_get` — ФИО и активность по списку ID, включая уволенных (`employee_search` ищет только работающих).

## Звонки

- `telephony_calls_list`: `recordFileId` (RECORD_FILE_ID звонка или первый файл дела-звонка CRM — у внешних АТС запись
  лежит в FILES дела; файлы ищутся одним `crm.activity.list` с `select: FILES` на страницу, если портал поле не
  вернул — `crm.activity.get` по делу), `userName`, `answered`. Фильтры `direction`, `status`, `minDurationSec`,
  `lineNumber`, `crmBound`, `phoneLast4` проверяются сервером (в портал уходят только период и сотрудник).
  `compact=true` (по умолчанию) убирает длинный `callId`, категорию и пустые поля. `mode=summary` — сводка по
  сотрудникам и линиям за весь период одним вызовом (до 50 000 звонков).
- `calls_recordings_download`: записи за период по тем же фильтрам → `DOWNLOAD_DIR/звонки`, имя
  «дата_время_сотрудник_вх|исх_длительность_call<ID>», опись `_список-файлов.csv` (номер под маской).
  Повтор пропускает уже скачанные без запросов к порталу.
- `call_transcribe`: запись (дело, файл Диска или уже скачанный файл) → текст с отметками времени.
  `scripts/transcribe/transcribe.py` запускается без оболочки из `TRANSCRIBE_PYTHON` (python с `faster-whisper`);
  модель `TRANSCRIBE_MODEL` (по умолчанию `small`), подсказка слов `TRANSCRIBE_HOTWORDS` + параметр `hotwords`.
  Стерео-запись (стороны в разных каналах) делится на «Собеседник 1/2»; моно — одним текстом. Текст сохраняется
  рядом с записью (`.transcript.json`, `.txt`), повтор не распознаёт заново. В CRM ничего не пишется: сохранить
  текст — `crm_timeline_comment_add` (с подтверждением человека) по `crmTarget` из ответа. Только `single`.

  Установка на сервере: `python3 -m venv ~/whisper && ~/whisper/bin/pip install faster-whisper`, затем в `.env`
  `TRANSCRIBE_PYTHON=/home/<user>/whisper/bin/python`. Первая расшифровка скачивает модель.

## Открытые линии

- `openlines_dialogs_list`: диалоги за период — сессии из дел CRM открытых линий (`PROVIDER_ID=IMOPENLINES_SESSION`,
  `ASSOCIATED_ENTITY_ID` — ID сессии, активные в периоде: `>=LAST_UPDATED from`, `<=CREATED to`), по каждой —
  `imopenlines.session.history.get`: канал (по ID коннектора: WhatsApp, Telegram, Max…), линия, оператор, клиент,
  привязка CRM, сообщений клиента/оператора, кто последний, `waitingReply`, время первого ответа. `waitingOnly`,
  `channel`, `lineId`, `operatorId`; до `maxDialogs` за вызов.
- `openlines_chat_history`: `from`/`to`, `textOnly` (без «оператор начал работу», «диалог завершён»).
- `openlines_chat_export`: переписка в `.txt` в `DOWNLOAD_DIR/переписка`.

## Не проверено на живом портале (mock-тесты)

- `start=-1` и `>ID` в `crm.*.list` на объёме портала; скорость при реальном лимите.
- `FILES` в ответе `crm.activity.list` (запасной путь — `crm.activity.get`).
- Поля дел открытых линий (`ASSOCIATED_ENTITY_ID` = ID сессии) и названия коннекторов Wazzup.
- `call_transcribe` с настоящим faster-whisper и стерео-записями внешней АТС (в тестах распознавание подменено скриптом).
