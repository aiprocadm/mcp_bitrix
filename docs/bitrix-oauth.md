# OAuth Bitrix24 и локальное приложение (ТЗ §6.2) — не реализовано

Состояние на 2026-09-24: сервер работает только через входящий вебхук. `BITRIX_AUTH_MODE=oauth` намеренно
отклоняется при старте (`CONFIG_INVALID`), поля `BITRIX_CLIENT_ID`, `BITRIX_CLIENT_SECRET`, `BITRIX_REDIRECT_URI`,
`BITRIX_INSTALL_URL`, `BITRIX_OAUTH_TOKEN_ENDPOINT`, `BITRIX_EXPECTED_MEMBER_ID`, `BITRIX_ACCESS_TOKEN`,
`BITRIX_REFRESH_TOKEN` принимаются схемой, но не используются. Таблица `oauth_tokens` в SQLite создана заранее.

## Когда это понадобится

- Метод отвечает `WRONG_AUTH_TYPE` (у нас `BITRIX_APP_CONTEXT_REQUIRED`): нужен контекст приложения.
- Нужна работа от имени авторизующегося сотрудника, а не фиксированного владельца вебхука.
- Нужны события установки/удаления или несколько порталов.

## Что будет сделано (этап 13, по §6.2)

1. `auth/oauth-provider.ts` реализует `BitrixAuthProvider`: `getAuth` подставляет `auth=<access_token>` в тело,
   `tryRefresh` — один refresh на пару портал/пользователь под блокировкой, новая пара сохраняется атомарно
   в зашифрованном `oauth_tokens`; при `invalid_grant` — стоп и требование переподключения.
2. `/integrations/bitrix/install` принимает установку только для заранее разрешённого портала, в ограниченное
   время, с одноразовым bootstrap-nonce; `application_token` из первого запроса не считается доказательством —
   проверка безопасным запросом к разрешённому порталу, затем атомарная активация. Перезапись действующих
   credentials без запроса запрещена.
3. Для code flow: `state`, точное совпадение redirect URI, защита от повторного callback, PKCE где поддерживается.
4. Bootstrap-токены из `.env` импортируются в хранилище один раз и удаляются из `.env`.

Тест-кейсы: T17 (один refresh на несколько запросов), T18 (подмена install endpoint/домена). OAuth Bitrix24 и
OAuth-защита самого MCP (этап 12) — разные контуры, предположения между ними не переносятся.
