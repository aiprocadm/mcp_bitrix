# Эксплуатация (ТЗ §8.6, §17.7)

Простыми словами: у сервера три ценности, которые нельзя потерять и нельзя смешивать в одном месте:
секрет вебхука (в `.env`), ключ шифрования (`data/secrets/master.key`) и база с журналом и планами (`data/mcp.sqlite`).

## Резервная копия

```bash
npm run backup                      # → data/backups/mcp-backup-<дата>.enc
npm run backup -- --out /backups/mcp-2026-09-24.enc
```

Что внутри: согласованный снимок SQLite (через `VACUUM INTO`, безопасно при WAL) и рабочие `policies/*.json`, всё
зашифровано AES-256-GCM ключом из `SECRETS_KEY_FILE`. Чего внутри нет намеренно: ключа и `.env`.
Ключ храните отдельно от копий (менеджер паролей, сейф); `.env` восстанавливается из вебхука в портале.

Перед копией на рабочем сервере: включите `READ_ONLY_MODE=true` или остановите сервер, чтобы в снимок не попала
операция в состоянии `executing`. Копия с работающего сервера тоже согласованная, но такие операции после
восстановления станут `unknown` и потребуют сверки.

## Восстановление (T45)

```bash
npm run backup -- --restore /backups/mcp-2026-09-24.enc --to /tmp/restore-2026-09-24
```

Команда расшифровывает копию в **новую** папку (поверх существующей не пишет), проверяет контрольную сумму
и читаемость базы и печатает, сколько операций ждут решения. Дальше вручную:

1. Остановите сервер.
2. Замените `data/mcp.sqlite` (и `-wal`/`-shm` удалите) файлом из папки восстановления; при необходимости верните `policies/*.json`.
3. Запустите `npm run doctor`. Операции `executing` станут `unknown`, `prepared`/`approved` останутся ждать: ничего не исполняется само.
4. Проверьте `operation_status` по спорным операциям и объекты в Bitrix24 перед новыми записями.

Проверка восстановления — часть регламента: раз в квартал восстанавливайте копию в отдельную папку и запускайте
`doctor` с `DATABASE_URL`, указывающим на восстановленный файл.

## Панель владельца `/admin` (удалённый режим)

Панель — второй способ сказать «да» плану записи (первый — `npm run approval:review` на сервере) и единственный
способ подготовить файл для `disk_upload_file` удалённо (ТЗ §4.5, §8.2 п.3, §8.5). Включается `ADMIN_PANEL_ENABLED=true`
(только `MCP_TRANSPORT=http`). Вход **отдельный**: не токен MCP и не Bitrix24.

1. Пользователь: `npm run admin:user -- --name boss --principal owner` (пароль ≥ 12 символов вводится скрыто,
   через pipe команда отказывает). `--principal` — запись из `policies/access.json`; её роль определяет права в панели:
   `administrator` решает по планам всех операторов, `operator` — только по своим, `reader` — только смотрит.
   `--list`, `--remove <имя>`; смена пароля закрывает сессии.
2. `https://<домен>/admin/login` → «Операции»: список планов, ожидающих решения, с оператором и сроком. Откройте план,
   прочитайте, что уйдёт в Bitrix24, введите слово `ПОДТВЕРЖДАЮ` или `ОТКЛОНЯЮ` — как в CLI. После «да» оператор
   повторяет вызов инструмента с теми же параметрами и `approvalId`. Подтверждение одноразовое.
3. «Файлы»: загрузите файл (txt, md, csv, pdf, docx, xlsx, png, jpg; до `MAX_UPLOAD_BYTES`) — получите `fileToken`
   для своего principal. При `UPLOAD_SCAN_REQUIRED=true` файл принимается только с вердиктом сканера `clean`;
   сканер недоступен — загрузка блокируется, файл не сохраняется.
4. Безопасность: cookie `HttpOnly; SameSite=Strict; Secure` (при https), сессия 8 ч (в базе — только хеш cookie),
   CSRF-токен в каждой форме + проверка `Origin`/`Sec-Fetch-Site`, пять попыток входа в минуту на имя, CSP без
   скриптов. Все решения и загрузки пишутся в `audit` с `tool=admin_panel`.

## Антивирусный сканер файлов

`UPLOAD_SCANNER_URL=clamd://127.0.0.1:3310` (или `clamd+unix:///var/run/clamav/clamd.ctl`) — демон ClamAV
по протоколу INSTREAM. На VPS проще всего `docker run -d --name clamav --network host clamav/clamav:stable`
(порт 3310 только на loopback) либо пакет `clamav-daemon` вашей ОС; базы сигнатур обновляет `freshclam`.
`npm run doctor` шлёт `PING` и падает, если сканер обязателен, но не отвечает. Проверка живым EICAR-файлом
(`eicar.com.txt` из `eicar.org`) через панель: ожидается отказ «отклонён антивирусом: Eicar-Test-Signature».
Реальный ClamAV в этом проекте не запускался — протокол проверен на фальшивом демоне в тестах (`not-run`).

## Обновление версии

1. `READ_ONLY_MODE=true`, перезапуск; дождитесь, пока `approval:review --list` не покажет `executing`.
2. `npm run backup`.
3. В новой версии: `npm ci && npm test && npm run build`; посмотрите `src/storage/migrations.ts` — миграции только добавляют.
4. Замените код (или образ), запустите `npm run doctor`, верните `READ_ONLY_MODE=false` только после проверки.
5. Откат: допустим, пока схема БД совместима (миграции не удаляют столбцы); при откате ниже версии миграции —
   восстанавливайте копию, сделанную до обновления.

## Ротация и утечка секрета вебхука

- Ротация по плану: создайте новый вебхук в портале, замените `BITRIX_WEBHOOK_BASE_URL` в `.env`, перезапустите,
  `npm run doctor`, затем удалите старый вебхук. Смена пароля сотрудника вебхук не отзывает.
- При утечке (§17.7): `READ_ONLY_MODE=true` → удалить вебхук в портале → новый вебхук и `.env` → перезапуск →
  отклонить ожидающие планы (`approval:review` → ОТКЛОНЯЮ) → изучить `audit` в SQLite (`SELECT * FROM audit ORDER BY ts DESC`)
  → проверить объекты в Bitrix24 за период. Удаление секрета из последнего коммита не считается устранением утечки.

## Журналы и сроки хранения

- Технические логи — stderr (JSON, Pino) с редактированием секретов; ротацию делает systemd/journald или Docker.
- Аудит — таблица `audit` в SQLite, очистка старше `AUDIT_RETENTION_DAYS` (90) при старте.
- Курсоры, подтверждения, staged-файлы — по TTL (`CURSOR_TTL_SECONDS`, `APPROVAL_TTL_SECONDS`, `UPLOAD_TTL_SECONDS`).
- Ключи идемпотентности — `IDEMPOTENCY_TTL_HOURS` (168).

## Наблюдение

- `GET /healthz` — процесс жив (без Bitrix). `GET /readyz` — база и аудит доступны, число сессий.
- `npm run doctor` — раз в день/после изменений в портале: права, scope, доступность 21 метода MVP.
- Ежемесячно: `npm outdated`, обновление SDK/runtime через тесты и новый lockfile (`docs/compatibility.md`).
